## Phase 1 — Payments: custom methods + paid/due shown properly (all 3 apps)

Findings: backend payment `method` is already a free string (`z.string().max(40)`) and
nothing filters by "cash"/"online" — the gap is UI. Web/desktop orders already have
RecordPaymentDialog + paid/due lines; mobile order payments are amount-only (no
method/note); bill forms hardcode Cash/Online.

1. **Shared `PaymentMethodPicker`** in `@munim/ui`: presets Cash · UPI · Card · Cheque ·
   Bank transfer + "Custom…" free text (max 40). Replace Cash/Online segments in:
   web/desktop/mobile bill forms ("Amount paid now"), `RecordPaymentDialog`
   (invoices + orders, all 3 apps), mobile order payment sheet.
2. **Bill-form paid/due strip**: live "Paid ₹X · Due ₹Y" summary near the totals on
   New Bill in all 3 apps (total − discount − material-returned value − paid).
3. **Mobile parity**: order + invoice record-payment gains method + note.
4. **Order payment history**: new `order_payments` ledger table (mirrors invoice
   payments), `POST /api/orders/:id/payments` records + returns updated order,
   `GET /api/orders/:id/payments` lists; Payments section in order detail on all 3.
5. **Invoice detail payments-section parity** on desktop + mobile (web has it).

## Phase 2 — Dashboard & Reports: weight sold + material received + period filters

Findings: `DashboardStats` has no period filter and no weight/material KPIs; reports
have free date inputs only; bills carry `materialReturnedWeight/Value/Title`.

1. **Core `getDashboard(db, period?)`**: optional `{from,to}` + new KPIs:
   `totalWeightSoldGm` (line-level frozen `pricing.weightGm` × preferred over product
   weight), `materialReceived` (parsed gm sum of `materialReturnedWeight`),
   `materialReceivedValue`. Report rows gain the same two aggregates + CSV columns.
2. **UI (all 3)**: Dashboard period chips (Today / This week / This month / Custom) +
   new KPI tiles; Reports quick-filter chips (Today / This week / This month / Custom
   dates) feeding existing start/end params; totals row shows weight sold + material
   received; CSV export includes them.

## Phase 3 — Articles (behave like category) + dedicated page + analytics (all 3)

Findings: categories are a dedicated `categories` table with `products.categoryId`;
articles will mirror this exactly.

1. **Schema**: `articles` (id, name unique, code?, description?, createdAt) +
   `products.articleId` FK (set null). `drizzle-kit push` + generated SQL committed.
2. **Core services + API**: articles CRUD; product create/update/list accepts +
   joins article (filter, search, dropdown); `GET /api/articles/analytics`
   (per-article stock count/value, sold units, sold weight gm, revenue, last-sale,
   6-month trend — reusing report query patterns).
3. **UI (all 3)**: Articles page — CRUD table/dialogs + analytics section (top
   articles by revenue/weight/stock-value, per-article detail with monthly trend,
   reusing dashboard/report chart components). Product form gains "Article" select
   next to Category; products table gains Article column + filter.
4. Nav entries + `docs/features.md`.

## Phase 4 — Bulk product edit (desktop page + web parity)

1. **API**: `PATCH /api/products/bulk` — `{ids[], patch{categoryId?, articleId?,
   priceMode?, labourType?, labourValue?, silverPercentage?, stockDelta?, active?}}`,
   zod-validated, returns count, writes activity log.
2. **Desktop "Bulk Edit" page**: filter bar (type/category/article/search) → checkbox
   table + select-all → patch panel → confirm → result toast. Separate sidebar page.
3. **Web**: same page (AGENTS §4b parity rule) unless user opts desktop-only.

## Phase 5 — Help overhaul + exhaustive documentation (all 3)

1. **Shared structured help content** in `@munim/ui` (sections data): every page, every

2. **Repo docs**: `docs/pages.md` mirroring the content; `docs/features.md` updated.

## Phase 6 — Web responsiveness + production-grade polish
